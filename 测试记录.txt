# 问题报告：`/v1` OpenAI 兼容接口首帧 8 秒延迟

## 结论（TLDR）

**不是架构问题，是冷启动问题。** `first_role_seconds ≈ 8s` 只发生在**每次服务重启后的第一个 `/v1/chat/completions` 请求**：请求处理器内的延迟 import（`agents.orchestrator` → langchain_openai → transformers → **torch**）在返回任何字节之前阻塞了 8.9 秒。热态下同一链路首帧仅 **0.17–0.18 秒**，整轮 4–5 秒，非常健康。协议层设计（role 首帧先于一切 agent 工作）本身正确且有回归测试保护。修复方向是**启动时预热**，不是改架构。

## 实测数据（生产服务器，单 worker，18:45 启动的冷进程）

| 测试项 | 结果 |
|---|---|
| `GET /health` ×5（回环） | 2–12 ms |
| `GET /v1/models` ×5（含 DB 鉴权） | 首次 55 ms，后续 3.7–4.6 ms |
| **`/v1/chat/completions` 冷态第 1 次**（回环） | **ttfb = 8.876s，first_role = 8.876s**，first_reasoning = 10.90s，first_content = 11.72s，整轮 15.0s |
| 热态第 2、3 次（回环） | **first_role = 0.169s / 0.184s**，first_reasoning = 0.76–0.80s，整轮 4.1–4.7s |
| 公网 `https://paper-agent.ycr10.cn/v1`（Nginx+TLS） | first_role = 0.181s，与回环无差 |
| 非流式 `stream:false`（热态） | 1.52s 完整返回 |
| 同 sessionId 两轮（checkpoint 保存/别名命中恢复） | 恢复零可测开销（第 2 轮反而更快：1.82s） |
| 进程 RSS | 冷 66.7 MB → 首个请求后 357 MB（torch 已在进程内加载，坐实 import 在请求路径上） |

**import 分解**（3 个全新子进程，wall 9.55–9.91s，峰值内存 ~308 MB）：

```
agents.orchestrator → agents.tools_impl → core/llm.py:14 langchain_openai (累计 5.79s)
  → langchain_openai.chat_models.azure → langchain_core.language_models.base
  → 尝试 transformers.GPT2TokenizerFast → modeling_gguf_pytorch_utils → import torch
按包自耗时：torch 2.78s | openai 0.91s | transformers 0.87s | langchain_openai 0.66s | langsmith 0.27s
```

## 根因链（文件:行号）

1. `backend/app/api/v1/openai_compat.py:610` — `from agents.orchestrator import chat_turn` 在请求 handler 内延迟执行，位于 `StreamingResponse` 返回之前，因此 role 首帧（`:828`）被 import 阻塞。
2. `backend/app/main.py:18-20` — FastAPI lifespan 为空，启动时无任何预热；systemd unit 无 `ExecStartPre`；runbook 的模型预热脚本是**独立进程**，只能暖磁盘缓存，暖不了 Uvicorn 进程内的 Python 模块。
3. torch 被拉进来是 langchain_core 的间接依赖（`GPT2TokenizerFast` → GGUF utils → `import torch`），不是业务需要——但这 9 秒里 torch+transformers 占 3.65s，其余是 openai SDK + langchain 胶水。
4. web 渠道同样受影响（`chat.py:83` 函数内 import），修复对两个渠道都生效。

## 架构核对结论

逐项核对后**协议与链路设计全部合格**：role 首帧先于 checkpoint/媒体/agent 工作（有 `test_stream_role_frame_precedes_slow_turn_preparation` 回归测试）；Nginx `/v1/` 配置正确（`proxy_buffering off` + HTTP/1.1 + `X-Accel-Buffering: no` + 3600s 超时，公网实测零额外延迟）；鉴权毫秒级；checkpoint 保存/恢复零开销；SSE 合帧仅 50ms；心跳 10s 不会抢先伪装首帧。唯一问题在**启动生命周期**。

## 顺带发现的观测缺口（这次“慢但看不到慢在哪”的直接原因）

1. `openai_compat.py:1062` 的 `openai_stream_complete` 计时日志（含 elapsed_ms/max_idle_ms）**从未进入 journal**——本次 7 条请求的 access log 都在，计时行 0 条：root logger 无 handler，INFO 被 lastResort 阈值吞掉。
2. 服务端没有任何 first_role/TTFT 维度指标，只能靠客户端脚本测量。
3. `api_trace_aggregates.total_latency_ms` 是 **span 时长累加**（llm_call + 各工具调用之和，`core/trace.py:69`），不是请求墙钟时间——今天 27 请求 avg 844s 是重度论文调研轮次的正常反映，使用时需防误读。

## 次要每请求开销（不构成 8 秒，修复时可顺带评估）

每请求 3 次重复 `ApiStorageStore.initialize()`（checkpoint store / StoragePressureGuard / Trace 各一次）；`user_store._connect()` 每次重复建表 DDL；无条件的 `run_cpu_bound(_attachment_context)` ≥10ms；历史 >10 条时 `_compress_history` 额外一次非流式 LLM 往返（影响 first_reasoning）；无 reasoning 模型下 160 字符 hold 缓冲推迟 first_content；README/DESIGN 写心跳 15s 而代码是 10s（文档不一致）。

# 修复详细计划（供你在开发机执行）

## 1. 核心修复：启动预热 `backend/app/main.py`

```python
import asyncio, logging, time

prewarm_logger = logging.getLogger("app.prewarm")

def _prewarm_agent_stack() -> None:
    t0 = time.monotonic()
    try:
        import agents.orchestrator  # noqa: F401  拉起完整 langchain/torch 链
        import tools.export.cards   # noqa: F401
        from core.llm import get_llm
        get_llm("light")  # 首次构造 ~0.9s，纯本地无网络调用
        prewarm_logger.info("agent stack prewarm done in %.1fs", time.monotonic() - t0)
    except Exception:
        prewarm_logger.warning("prewarm failed; first request will lazy-import", exc_info=True)

@asynccontextmanager
async def lifespan(app: FastAPI):
    task = asyncio.create_task(asyncio.to_thread(_prewarm_agent_stack))
    try:
        yield
    finally:
        task.cancel()
```

要点：**后台线程执行**——服务立即对外监听（`/health` 不被 9 秒阻塞），预热期内到达的首个 `/v1/chat` 最多等剩余 import 时间（模块锁串行）；**全程 try/except 优雅降级**，预热失败回退到现有请求内延迟 import，绝不阻断启动；shutdown 时取消未完成任务。代价：启动多 ~9–10s（后台）、常驻 RSS +约 290 MB（本来首个聊天请求也会加载，4C16G 目标环境无压力）。`openai_compat.py:610` 的延迟 import **保留不动**，作为降级路径。

# 问题报告：工具调用“死循环”根因（以 openai-compatible-agent-integration-guide.md 为验收标准）

## 结论（TLDR）

**不存在真正的死循环**（ReAct 有 `_MAX_ITERATIONS=8+4` 硬上限，SVG 生成是纯 Python 模板不可能循环）。用户看到的“死循环”是三个真实缺陷叠加的表现：

1. **`search_papers` 慢且在 /v1 渠道必被腰斩**：/v1 给它的工具预算是 45 秒（`tools_impl.py:33`），而这条多阶段流水线（LLM 理解→6 源联邦检索→本地重排→OA 全文探测→持久化索引）在现行策略下需要 70–140 秒。实测两轮：检索源 27 秒就全部完成，但后续阶段在 45 秒预算处被杀，**整个工具以“没有拿到结果”告终，27 秒的检索成果全部丢弃**。
2. **超时语义诱导重试**：超时文案“请使用已完成的结果回答，或建议用户下一轮缩小范围后继续”（`tools_impl.py:167-169`）——但成果已被丢弃，模型实际拿到的指令等于“重试”；实测场景 1 中模型确实立刻发起了第二次搜索，再次被腰斩，直到 95 秒软时限优雅收场，用户只收到一段道歉文字。且 **TIMEOUT 不计入熔断器**（`tools_impl.py:174-178` 只记 `TOOL_ERROR`），模型可在迭代上限内反复重搜。
3. **web 渠道无任何时限**：`chat.py:130-160` 只有 15 秒心跳，无整轮时限、无工具级超时——旧策略下 `search_papers` 实跑 203/245/296 秒，用户只能关页面（trace 里的 `CancelledError ... RequestResponseCycle.run_asgi` 就是断连证据）。web 侧最坏情况是模型重搜到迭代上限，理论可达十几分钟——这就是“卡死”体验。

**连带后果**：搜索被腰斩后会话里没有任何论文 → `research_map`/`deep_read`/`ask_papers`/`write_review`/export 在 /v1 上**结构性无法到达**（实测地图轮在无论文时 3.5 秒礼貌反问，路径本身健康）。“生成图谱死循环”实为“搜索永远供不出论文集”。

   - 场景 2（正常链路）：先 search_papers 再要图 → 记录 research_map 全程耗时、心跳帧数与间隔（心跳 10s/次 → 心跳数×10s ≈ 工具阻塞窗口）、x_soda.attachments 是否含 SVG 文件卡片。
3. **其他工具逐项计时**：deep_read（选一篇短 OA 论文）、ask_papers、export（research_map → md）、write_review（时间允许时）——每项记录 first_role/first_reasoning/first_content/总时长/心跳数/错误帧，与阶段 B 超时表对照。
4. **逐层排除矩阵**（结论按此归因）：网络/Nginx（已排除）→ 鉴权路由（已排除）→ 协议帧层（C1）→ ReAct 循环层（A1+B1）→ 单工具层（C2/C3+trace latency）→ 子 agent/SVG 生成层（B3+trace）。
5. **安全边界**：全程串行、每轮等闭合后再发下一轮；任何单轮 >110s 未闭合即记录并停止该场景，绝不在生产并发压测；web 渠道不做长循环主动复现（防占死单 worker），以 trace 证据 + 代码结论替代。
